# Subagent brief: rewrite one crate's release section

You are rewriting the newest release section of the `{{package}}` changelog in
the repository at `{{root}}`.

## Inputs

- Changelog: `{{changelog}}`
- Crate directory: `{{crate_dir}}`
- Previous release tag: `{{prev_tag}}`
- New release heading: `{{heading}}`
- Release date: `{{date}}`
- Commit digest: `{{commit_file}}`
- Style guide: `{{style_guide}}`
- Repository for links: `bitcoindevkit/bdk`

## Critical context

The section currently at the top of the changelog was generated by release-plz
and is **not** a reliable source of truth. It may include years-old commits,
CI/docs/test noise, duplicates, and changes that belong to another crate.
Rebuild the section from `git log {{prev_tag}}..HEAD` and verify names and
behavior against the source at `HEAD`.

## Steps

1. Read the changelog and the style guide.
2. Read the commit digest at `{{commit_file}}`, then run:
   ```bash
   git log --oneline {{prev_tag}}..HEAD -- {{crate_dir}}
   git log --oneline {{prev_tag}}..HEAD
   ```
   Use `git show <sha>` and read `{{crate_dir}}/src` to understand each
   user-visible change. Use
   `gh pr view <N> --repo bitcoindevkit/bdk --json title,body,files` when the
   subject is not enough. If `gh` is unavailable or the PR is inaccessible,
   fall back to `git show` plus the commit message.
3. Build the list of user-facing changes for `{{package}}` only:
   - public API additions, removals, renames, and behavior changes,
   - bug fixes users can observe,
   - MSRV and public dependency baselines,
   - breaking changes and migration notes.
   Exclude CI, docs, tests, formatting, clippy, internal refactors,
   dev-dependency bumps, example-only fixes, and release bookkeeping.
   Do not duplicate another crate's changelog; mention a dependency only when
   its change affects this crate's users.
4. Rewrite **only** the section from the release heading down to (but not
   including) the next `## ` heading.
   - Keep the heading line, but ensure the compare URL uses
     `https://github.com/bitcoindevkit/bdk/compare/...`.
   - Use `### Added`, `### Changed`, `### Fixed`, `### Removed`, in that order,
     only when non-empty.
   - Follow the style guide: imperative bullets, backticked identifiers,
     `**Breaking:**` prefix, inline PR or commit links.
   - Prefer the final API at `HEAD`; never describe intermediate APIs that were
     introduced and removed within the same cycle.
5. Do not edit `Cargo.toml`, other crates, or anything outside the changelog.
   Do not stage or commit.
6. Verify:
   - `git diff -- {{changelog}}` touches only the release section.
   - Every API name is confirmed with `grep -rn` or codegraph.
   - Every `**Breaking:**` claim is supported by the diff or PR.
   - The text below the section is byte-for-byte unchanged.

## Report

Return:

1. The final section text.
2. Any claims you were uncertain about and changes you deliberately excluded.
3. Confirmation that the rest of the file is untouched.
